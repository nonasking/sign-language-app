# KSL 개발 오케스트레이터

feature-builder와 qa-reviewer로 구성된 에이전트 팀을 구성하여 기능 개발 사이클을 완료한다.

**실행 모드:** 에이전트 팀 (feature-builder + qa-reviewer)

---

## Phase 0: 컨텍스트 확인

작업 시작 전 현황을 파악하여 실행 모드를 결정한다.

1. `_workspace/` 디렉토리 존재 여부 확인
   - 없음 → **초기 실행**
   - 있음 + 사용자가 부분 수정 요청 → **부분 재실행** (해당 에이전트만 재호출)
   - 있음 + 새 요청 → `_workspace/`를 `_workspace_prev/`로 이동 후 **새 실행**

2. 요청의 규모 파악
   - **단순 변경** (1~2 파일, 명확한 범위): Phase 1~3 간소화
   - **복합 변경** (다수 파일, 아키텍처 영향): 전체 Phase 실행
   - **설계 결정 필요** (구조 변경, 새 의존성): 구현 전 사용자 확인

---

## Phase 1: 작업 명세 작성

1. 사용자 요청을 분석하여 구체적인 작업 명세를 작성한다:
   - 수정할 파일 목록
   - 기대 동작 (Before/After)
   - 주의사항 (기존 패턴 유지, 좌표계 등)

2. 요청이 아래에 해당하면 **구현 전 사용자 확인**:
   - 컴포넌트 분리/합치기
   - 새 npm 패키지 추가
   - 좌표계 또는 포즈 데이터 형식 변경
   - Three.js 씬 구조 대규모 변경

---

## Phase 2: 팀 구성 및 작업 할당

```
TeamCreate("ksl-dev-team", ["feature-builder", "qa-reviewer"])
```

feature-builder에게 작업 명세를 전달한다:
```
작업: [요청 내용]
수정 파일: [파일 목록]
기대 동작: [Before → After]
주의사항: [좌표계, 패턴 등 특이사항]
완료 후 qa-reviewer에게 리뷰 요청할 것
```

---

## Phase 3: 구현 및 QA 사이클

1. feature-builder가 구현을 진행한다
2. 구현 완료 → qa-reviewer에게 리뷰 요청
3. qa-reviewer가 체크리스트 기반 검증
   - 승인 → Phase 4
   - 수정 요청 → feature-builder 재작업 → 재검증 (최대 2회 반복)

---

## Phase 4: 완료 및 커밋

qa-reviewer 승인 후:

1. `npm run build` 최종 확인
2. 커밋 준비:
   - **커밋 메시지는 한국어**로 작성
   - **Co-authored-by: Claude 절대 포함 금지**
   - 형식: `type(scope): 내용`
   - 예시: `feat(avatar): 손 관절 색상 손가락별로 구분`
3. 사용자에게 커밋 메시지 제안 후 확인받고 실행

---

## 에러 핸들링

| 상황 | 처리 |
|------|------|
| 빌드 실패 | feature-builder에게 에러 전달, 수정 요청 |
| QA 2회 반복 실패 | 오케스트레이터가 직접 문제 진단 후 접근 방식 재검토 |
| 설계 결정 필요 | 구현 중단, 사용자에게 보고 및 확인 요청 |

---

## 후속 작업 처리

이전 `_workspace/`가 있을 때:
- feature-builder는 기존 변경사항을 먼저 읽고 일관성 유지
- "이전 결과 기반으로", "방금 한 거 수정" 등의 요청은 부분 재실행으로 처리

## 테스트 시나리오

**정상 흐름:**
"Three.js 아바타에 배경 그라디언트 추가해줘"
→ Phase 1에서 SignAvatar.jsx 수정으로 명세 → feature-builder 구현 → qa-reviewer 승인 → 커밋

**에러 흐름:**
"새 포즈 추가했는데 애니메이션이 멈춰요"
→ Phase 0에서 기존 workspace 확인 → 부분 재실행으로 qa-reviewer가 POSES 키 정합성 검증 먼저 수행
